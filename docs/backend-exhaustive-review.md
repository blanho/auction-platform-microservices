# Backend file review

## Coverage and method

The [file ledger](backend-file-audit.csv) records every tracked or newly added file under `src/`, `deploy/`, and `.github/`, plus the root build configuration as reviewed on 2026-09-25: **1,625 files**, including 1,419 C# files, 82 project files, 30 JSON files, 24 resource files, 38 YAML files, 11 Dockerfiles, four protobuf files, and 17 other build, script, and documentation files. Each row records its path, size, content hash prefix, validation result, depth of inspection, and code signals requiring attention. All files were read by the inventory scan; JSON, XML, and YAML parsed successfully. All three Kubernetes overlays rendered locally with `kubectl kustomize`. The solution compiled with the latest analyzer level and **zero warnings or errors**. The follow-up full test suite passed **165 tests**. Formatter verification initially found six diagnostics in two test files; those were fixed and verification was rerun.

Forty-nine files received focused manual inspection, including the main query, messaging, authorization, storage, payment, worker, and saga paths. The ledger explicitly marks the other files as **automated inspection**. This is complete file coverage for inventory, validation, and selected risk signals; it is not a claim that every line of every file received human semantic review or live service testing. A build and a green test suite do not prove absence of runtime bugs.

The initial audit did not change public APIs, schema, transaction boundaries, message contracts, or provider behavior. Follow-up work serialized scoped database access in analytics, identity, and notification handlers and corrected the import skip count to use the current import checkpoint. Pre-existing local-file storage edits were preserved in the branch.

The ledger hashes reflect the initial audit snapshot; files changed during follow-up have newer contents, and new follow-up files are not in that snapshot.

## Follow-up status

- Analytics and two-factor status handlers now await shared-context queries in order. The analytics aggregation repository does the same. Notification sends remain concurrent, while each consumer serializes record additions and saves through its scoped unit of work.
- Import results now report valid rows skipped from the current checkpoint. The public `CountByCorrelationIdAsync` repository method remains for API compatibility, but its implementation cannot correctly count by correlation because auctions have no correlation field. It is no longer used by the import handler.
- A follow-up registration check found that Auction's queued import, export, and bulk-update consumers are absent from its MassTransit setup. Those workflows need message-contract and result-delivery fixes before enabling them; the import batch repository saves chunks independently, and the existing job-progress messages are not idempotent. Bulk insert and update loops no longer materialize their entire chunk lists before processing.
- Report generation now writes real XLSX and PDF files, aligns specialized headers with their rows, aggregates seller payout and revenue from paid non-refunded orders, and applies buyer/seller filters in SQL before loading every matching order. The order model has no refund reason, so the refund report includes only available fields. The report filter query was exercised against PostgreSQL.
- Report jobs now upload generated bytes to Storage through an API-key-protected internal endpoint before publishing completion. The event carries an authenticated, owner-only download route. The Storage service blocks direct static access and generic URL/SAS endpoints for private reports. Provision `auction-platform-report-storage-api-key` in the production Key Vault before deployment.
- Batch uploads now propagate caller cancellation and make best-effort blob rollback without replacing the original database exception. Bidding batch repositories enumerate single-use inputs once. Top-auction analytics counts bids only for the selected auctions. Payment revenue and order statistics now aggregate in SQL without loading each order.
- PostgreSQL checks found that Payment's daily revenue and top-performer projections could not be translated; their aggregation and limiting now run in SQL, followed by DTO construction. Fresh Payment orders and wallets also failed insertion because their required `UpdatedAt` columns received null; both factories now initialize it to the creation timestamp. The Payment aggregates, report filter, top-performer queries, inserts, and analytics top-auction query passed against a disposable PostgreSQL 16 container. The follow-up Payment infrastructure and domain test projects passed 13 and four tests, respectively.
- Message broker verification is still needed. The disposable PostgreSQL check did not exercise migrations or the full service stack.
- The Job worker now propagates cancellation during dispatch and stuck-job recovery instead of treating shutdown as a job failure. `RequestJobCommand` requests with a positive `TotalItems` and no explicit items use the external-progress path; requests with explicit items, and requests without a positive total, create job items for the dispatcher. Only the latter path is affected by the missing `ProcessJobItemCommand` consumer.
- Job item batch insertion now enumerates caller input once when assigning audit fields and adding items to EF. Existing lists and arrays are reused without allocation.
- Auction queued export now uploads generated CSV or JSON bytes through Storage's private report endpoint before publishing completion, and passes the owner-only download route to the completion event. Auction is wired to the existing report-storage credentials in Docker and Kubernetes. The export consumer is still unregistered pending the Job progress and retry fixes; this change does not activate the queued endpoint.
- Storage now applies its advertised 50 MiB limit to private report uploads while keeping ordinary uploads at their configured 10 MiB limit. Ordinary single-file, batch, and presigned-upload routes reject the reserved `private-reports` folder, so only the API-key-protected internal route can create private report records.
- All three Auction import paths now count rejected rows instead of validation messages when reporting failed totals; detailed field errors are unchanged. The single-message import consumer also uses the shared batch-size constant instead of a duplicate literal. Tests cover a row with multiple validation errors in each path.
- Catalog category updates and soft deletes now mark only the category root as modified. `GetByIdAsync` still includes children for read responses, but saving a detached root no longer writes those unchanged children. Delete-by-ID loads one tracked root without its child collection; change-tracker tests cover root-only updates and deletes.
- Catalog's remaining handlers and brand paging query received a focused pass. Category parent-hierarchy checks still load child collections from `GetByIdAsync` at each ancestor; this is a query-size concern for wide trees, but changing that repository contract solely for this optimization was deferred. Search's Elasticsearch services now propagate cancellation rather than converting it to empty or failure results, including when the client returns an invalid response for a canceled call.
- Bidding auto-bid persistence now forwards the existing cancellation token to its repository update. The winning-bids read path was inspected: it does not have Payment state, so its `IsPaid` filter is ignored and its DTO always reports an unpaid/default status. Correct payment status requires an explicit cross-service contract.
- Notification bulk progress now reports counts for each batch rather than cumulative counts, matching Job's additive progress contract. Recipient cancellation propagates instead of being counted as a failed delivery; two focused consumer tests cover both cases.
- Notification sender adapters, the application sender, and the in-app event consumer now propagate `OperationCanceledException` instead of recording or logging canceled requests as delivery failures. Focused tests cover the default email, SMS, and push adapters and the application email path.
- Notification bulk reports now count a recipient as failed if any requested delivery channel returns a failed result. Its existing idempotency marking remains unchanged, so a recorded channel failure does not automatically retry; changing retry semantics requires a separate design decision.
- Job single-item and batch-result consumers now reject item results whose item belongs to a different job. Focused tests verify that a mismatched single result leaves its item untouched and a mixed batch updates only the owning job's item and count.
- The Job worker's pending-job query now selects only jobs with non-deleted, pending items to dispatch. External-progress jobs, which intentionally have no items, remain Pending until a progress message starts them; this prevents the worker from starting them and dispatching zero items.
- The follow-up `auction.sln` build, including the new Notification and Job infrastructure test projects, completed with zero warnings and errors.
- Auction's bulk-update consumer now propagates cancellation from an individual write instead of counting it as a failed auction. It now reads each batch as tracked auctions with item titles and updates only changed EF properties; one test covers the batch call, title-bearing domain events, and progress counts. The queued consumer still needs its registration and job contract repaired before activation.
- Active Buy Now reserve, complete, and release consumers now load tracked auctions for writes, forward cancellation to those reads, and propagate it. Reserve and complete no longer publish business-failure events when their work was canceled. The repository leaves tracked related entities unchanged, while keeping detached-update behavior; focused consumer and change-tracker tests cover these paths.

## Signals checked across every C# file

The ledger flags code for inspection; a flag alone does **not** mean a defect. It found broad `Exception` catches in 44 files, parallel work in 14, async EF queries in 44, enumerable inputs in 75, and route mapping in 35. The broad-catch review distinguished logging/rethrow and deliberate best-effort operations from cancellation-sensitive paths. Route mapping files were checked for authorization metadata. The two apparent exceptions use an admin `AuthorizeAttribute` on their route groups, so they are **not** reported as unprotected routes.

No `TODO`, `FIXME`, `HACK`, `NotImplementedException`, `async void`, blocking `.Wait()`, or blocking task `.Result` appeared in production C# paths from the targeted text scan. The `.Result` matches observed belong to result objects, not task blocking.

Development settings include local placeholder credentials and shared development secrets. Production-facing settings contain empty values intended for environment injection. This review does not assert that runtime secret injection or rotation is configured correctly.

## Remaining verification

PostgreSQL/EF was exercised only for the seeded Payment and analytics queries listed above. Message broker, Elasticsearch, Redis, Stripe, SMTP/SMS/push, and hosted-worker behavior was not exercised. Several test projects contain mainly assembly-reference tests, so runtime concurrency and report-delivery integration still need testing. The findings above are evidence-backed review results, not silent changes to production behavior.
